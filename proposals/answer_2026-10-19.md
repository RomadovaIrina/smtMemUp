# Ответ на вопросы от 19.10.2026: почему SMT работает на Stack, но не на MQAR, и абляции SMT

Все числа — validation / tuning, seed 107; test не использовался. Код и логи — в репозитории (ссылки в тексте).

## 1. Почему на Stack SMT работает, а на MQAR (associative recall) — нет

### Короткий ответ
Причина — **сжатие прошлого в небольшое число memory-токенов** (K = 8 векторов, из которых декодер читает всё
прошлое). Это показано прямым тестом: та же модель SMT-teacher с тем же loss на тех же данных учит связывание
ключ → значение на 100%, если декодеру открыть все выходы энкодера. Через 8 memory-токенов (как в SMT) — остаётся
на уровне угадывания. Длина примера, окно, бюджет и реализация loss причиной не являются.

### Интерпретация
* **Stack.** Ответ на pop определяется небольшим **состоянием**: что лежит на вершине и глубже. Энкодер может
  обновлять это компактное состояние, и оно хорошо ложится в 8 memory-токенов.
* **MQAR.** Нужно хранить **таблицу произвольных пар**, а при запросе адресовать её по содержимому (ключу).
  * В Transformer это делает внимание к нужной позиции прошлого.
  * В SMT весь доступ к прошлому — только через memory-токены. Их нужно научить кодировать связки так, чтобы декодер
    по ключу извлёк значение.
  * Градиентный сигнал на эту запись слабый: декодер получает лёгкий «обходной» сигнал — набор значений, пары из
    будущих входов. Обучение застревает на уровне «знаю набор значений, но не связку» (loss = ln N).
* **RNN с BPTT** той же архитектуры (память из memory-токенов) тоже не учит связывание. Это согласуется с
  наблюдением авторов SMT о провале на Keys-Values.
* **Следствие для продолжения:** нужны либо механизм записи / чтения памяти, адресуемый по содержимому (матричная /
  fast-weight память в updater), либо цель, напрямую требующая связки «память + ключ → значение». Пример — MemUP-цель
  «только по памяти» (`proposals/idea_smt_associative_recall.md`).

## 2. Абляции SMT на Stack (где SMT работает)
* **Эталон:** SMT с коротким окном Tf = 8, без дальних целей; бюджет SMT 11k / DMT 5k (зафиксирован правилом
  диагностики v4). Каждый прогон отключает один компонент.
* **Код:** `checks/smt_memup_ablation.py`.
* **Итоговая таблица и графики** (teacher, RNN до DMT, итоговая RNN после DMT, шаги до 80/95%):
  `outputs_ablation/README.md`. Сервер обновляет её и пушит автоматически по окончании очереди.

| абляция | что проверяет |
|---|---|
| без L_dyn | нужен ли сигнал динамики (обучение updater и марковость памяти) |
| detached: L_dyn не идёт в энкодер | роль совместного обучения (в статье: при коротком окне кредит «амортизируется» через L_dyn) |
| без L_unif | роль uniformity-члена |
| Tf = 1 / 4 / 16 / 64 | роль длины предсказательного окна |
| память 4 / 16 токенов | ёмкость памяти |
| RNN без DMT | берётся из SMT-стадии каждого прогона |

**Промежуточно (до DMT):**
* без L_dyn teacher достигает 100%, но RNN без DMT — 24%: без L_dyn updater не обучается в SMT. Восстанавливается
  ли RNN в DMT — в итоговой таблице.
* detached и без L_unif: teacher 98–99%.

**Полные кривые обучения** всех прогонов (каждые 500 шагов) — `outputs_v4/table_diag_histories.csv` и
`runs/*/…/*_history.csv`.
