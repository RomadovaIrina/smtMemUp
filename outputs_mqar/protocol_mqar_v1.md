# MQAR: протокол, версия 1 (14.10.2026). Записан до любых обучений MQAR

Все решения ниже — наши экспериментальные настройки (научник их не задавал). Код: `smt_memup_mqar.py`
(хэш входит в identity запуска `runs/mqar03_pilot01_<key>`), `smt_memup_stack.py` не менялся.

## Стартовая конфигурация: `pilot01`
Zoology `multiquery_ar` без шума (`random_non_queries=False`): словарь 128 (ключи 1–63, значения 64–127), длина 64,
N = 8 пар, K = 2, окно локального детектора r = 24, «дальний ответ» — давность ≥ 24 (38% ответов).
Модель, SMT/DMT, бюджеты, seeds — как в Stack (d=64, 8×64 памяти; SMT 3000 шагов, DMT 1500, batch 32, все anchors,
DMT от нулевого состояния по всей последовательности).

Почему эта конфигурация (а не та, что обещает наибольший выигрыш):
* **Отбор действительно выбирает.** При N = 8, K = 2 у 72% anchors пул будущих ответов больше K (средний пул 4,6).
  При N = 4, K = 1 (zoology_basic) — 39% anchors с пулом ≤ K, где все правила совпадают.
* **Связывание проверяемо.** Случайный уровень среди записанных значений 1/8 = 12,5%; уровень эвристики «r-й запрос →
  r-я пара» без связывания — 15,7% (замер на данных генератора); исключение уже спрошенных значений без связывания
  невозможно (ответы не подаются на вход).
* **Обучаемость при нашем бюджете.** Длина 64 со всеми anchors и DMT по всей последовательности — тот же путь кода,
  что в Stack (оценка ~3,4 ГБ, ~0,26 ч на обучение; уточняется замером). Маленький словарь: каждый ключ встречается
  в ~12 тыс. train-последовательностях за SMT, против ~190 при словаре 8192.
* Известный риск: в архивном пилоте 01 эта конфигурация при бюджете в 27 раз меньше дала 12,7% среди записанных
  значений — связывание не освоено. Поэтому сначала только baseline и gate.

## Окно r и почему перенос r = 8 со Stack неинформативен
Окно видит пару ключ–значение, только если запрос стоит не дальше r токенов от пары. Правило (до обучения):
наименьшее r из сетки, при котором пара видна окну хотя бы у половины ответов → r = 24 (57% видимых).
При r = 8 пара видна у 5% ответов: почти все ответы «неожиданны», идеальный surprise-K совпадает с random-K
(доля дальних среди выбранных 0,843 против 0,834). Окно Stack = 8 подобрано под давности Stack и ничего не говорит
о доступности пары в MQAR.

## Что различает отбор на MQAR (ограничение постановки, известное до обучения)
Все пары записаны в первых 2N = 16 токенах. Для anchors t ≥ 16 любой будущий ответ требует память m_t, поэтому
отбор не может усилить «ответы из памяти» сильнее случайного (идеальный surprise-K: 0,849 против 0,843; oracle 1,0;
по входам декодера 0,937). Surprise-K с окном 24 сдвигает вес к ответам, чья пара далеко от запроса (дальних
среди выбранных 0,786 против 0,625; средний сдвиг ответа от anchor 21,5 против 15,8). Т.е. на MQAR surprise-K —
это в основном усиление давних ответов, а не отбор ответов, которым нужна память. Слабое различие — свойство
постановки; его будем измерять (доля выбранных пар, отличие от random-K по позициям anchors), а не обходить.

## Адаптации относительно Stack
* Loss: тот же авторский SMT loss + α·L_sel, та же нормировка; логиты decoder считаются только в позициях ответов
  (математически то же, проверено тестом), anchors — все (T = 64).
* Anchors: все; подвыборка anchors (Monte Carlo) реализована для длинных конфигураций, здесь не используется.
* DMT: как в Stack — от нулевого состояния по всей последовательности.
* Метрики: полная CE/accuracy по словарю; **точность и CE среди N записанных значений** (`cand_*`); доля предсказаний
  из записанного набора; номер запроса и слот пары.
* α-сетка: {0,3; 1; 3}. В Stack все варианты выбрали α = 1 — край сетки {0,1; 0,3; 1}; сетка сдвинута до любых MQAR-данных.

## Детекторы (поправка 14.10, до любого обучения SMT на MQAR)
Первый аудит с настройками детекторов из Stack (embedding 16, GRU 64, 2000 шагов) дал недообученные детекторы:
окно — AUC «пара вне окна» 0,79, по входам декодера — AUC 0,64 (идеал 1,0). Каталог помечен как устаревший
(`runs/obsolete_mqar03_pilot01_037cb754085a_undertrained_detectors`), baseline в нём не обучался.
Пробы на CPU (только validation): GRU 64/128 — AUC 0,94 к 4000 шагам; трансформер с обучаемыми позициями — то же.
При этом точность при видимой паре у всех ~17–18% (уровень «одно из значений в окне»): локальный детектор не осваивает
связывание, но для top-K важно ранжирование, а оно близко к идеальному. Решение: embedding 64, GRU 128, 20 000 шагов,
best по validation CE (как в Stack). Критерий, который показываем: AUC ранжирования против идеального правила; точность
при видимой паре — как свидетельство, что детектор не решает MQAR сам.

## Gate baseline (пригодность)
Tuning-набор (512 последовательностей) с **перемешанным порядком запросов** (`shuffle_query_order`: те же пары и
позиции, ключи распределены по запросам случайно — порядок не несёт информации). Дальние ответы (давность ≥ 24),
точность среди записанных значений: teacher после SMT ≥ 1/8 + 0,10 = 0,225; RNN после DMT ≥ 1/8 + 0,05 = 0,175
(те же отступы, что в Stack). Дополнительно показываются: исходный порядок, полный словарь, первый запрос
(без какой-либо эвристики порядка), доля предсказаний из записанного набора.

## Если gate не пройден: заранее заданная лестница (только tuning seed, только validation/tuning)
1. Диагностика без обучения: точность среди записанных значений по позициям anchors и по номеру запроса; teacher vs RNN;
   кривые validation (растут ли ещё).
2. Бюджет: SMT 9000 шагов (×3), остальное без изменений.
3. Скорость обучения SMT 1e-3.
4. Ширина d_model = 128 (память 8×128).
Каждый шаг — новый каталог запуска; первый прошедший gate становится baseline для сравнения, все шаги
документируются. Test на этой стадии не создаётся. Полный подбор α — только после пройденного gate.
